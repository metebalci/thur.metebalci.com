# Security Policy

This repository serves the `thur.metebalci.com` landing page and
publishes the apt / yum repository at `pkg.thur.metebalci.com`. The
relevant security surface here is the **package signing chain**, the
**`install.sh` bootstrap script**, and the **CI workflows** that hold
the signing key and R2 credentials. Bugs in the Thur VTL / Thur VSA
binaries themselves belong to [`metebalci/thur`][thur-sec] — please
report those there.

[thur-sec]: https://github.com/metebalci/thur/security/policy

## Supported versions

Only the `main` branch is supported. Fixes land on `main` and ship via
the next deploy (Cloudflare Pages auto-deploys `main`; the package tree
is regenerated by the next `publish` workflow run).

## Reporting a vulnerability

**Do not open a public issue for a security vulnerability.**

Report it privately through GitHub: on this repository's **Security**
tab, use **"Report a vulnerability"** to open a private advisory
([GitHub Private Vulnerability Reporting][pvr]). The report stays
private until a fix is published.

[pvr]: https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability

## What to include

A useful report has:

- **Affected surface** — `install.sh`, signing / index integrity,
  `pkg.thur.metebalci.com` content, or a workflow / secret-handling
  bug.
- **Reproduction** — minimal steps, and what an attacker gains
  (e.g. arbitrary root command via the install pipeline, ability to
  serve unsigned or wrong-signed packages, ability to exfiltrate the
  signing key).
- **Affected commit / artifact** — for `install.sh`, the commit hash.
  For the package tree, the channel + the affected file path under
  `pkg.thur.metebalci.com/`.

## Response expectations

This is a solo-maintained project. Under normal conditions a report
is acknowledged within about **5 business days**; outside normal
conditions, handling is best-effort. After triage, a fix timeline is
communicated in the private advisory thread.

## Coordinated disclosure

Please keep a reported issue private until a fix is published or 90
days have passed, whichever comes first. Reporters are credited in the
published advisory by default — say so in the report if you prefer to
remain anonymous.

## Scope

In scope:

- **`install.sh`** — the script users pipe to `sudo bash`. Command
  injection, repo-wiring bugs, key-substitution attacks, or any path
  by which a tampered response from `pkg.thur.metebalci.com` could
  escalate beyond "package install fails".
- **Signing chain integrity** — the `pubkey.asc` served at the tree
  root, the `Release` / `InRelease` / `Release.gpg` files per apt
  suite, and the `repomd.xml` / `repomd.xml.asc` for the rpm tree.
  Reports of mismatched signatures, missing signatures, or weak
  signature configuration are welcome.
- **Workflow / secret handling** — the GitHub Actions workflows
  (`publish.yml`, `unpublish.yml`) that hold `GPG_PRIVATE_KEY`,
  `GPG_PASSPHRASE`, and the R2 credentials. Anything that could leak
  these to a fork PR, a third party, or workflow logs.
- **Repository tree access controls** — paths under
  `pkg.thur.metebalci.com/` that should be read-only-public being
  writable, or content being served from a wrong origin.
- **Pre-commit hook bypass** — ways the `.githooks/pre-commit` secret
  scan / license check can be silently sidestepped on a normal commit.

Out of scope:

- Bugs inside `thurvtl` / `thurvsa` themselves — see
  [metebalci/thur][thur-sec].
- Operator misconfiguration of an installed system (e.g. running
  `install.sh` on an unsupported distro and adapting it by hand).
- Cloudflare account / Cloudflare service vulnerabilities — report
  those to Cloudflare.
- Theoretical issues with no demonstrated practical impact.

## Current security posture

- **Key rotation procedure** is documented in [`README.md`][readme]
  § "Required Actions secrets". Old public keys are left on the
  keyserver after rotation so historical signatures keep verifying.
- The GPG signing key **fingerprint** is hardcoded in
  `.github/workflows/publish.yml` and `unpublish.yml` and is public by
  definition — it appears in every signed index. The private key and
  passphrase are the only secrets in the signing chain.
- Workflow permissions are scoped to `contents: read`. Publish and
  unpublish workflows trigger on `workflow_dispatch` (and `publish`
  also on `repository_dispatch` from `metebalci/thur`) — never on
  `pull_request`, so fork PRs cannot reach the signing key.
- Commits are gated by `.githooks/pre-commit` (gitleaks +
  license-header + author-identity), but only after a one-time
  `git config core.hooksPath .githooks`. The hook is a defence in
  depth, not a substitute for secret management — the signing key
  must never appear in the working tree, hooks or no hooks.
